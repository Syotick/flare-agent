# Flare Agent · 压测方案（Load Testing Plan）

> 版本：v0.1 ｜ 日期：2026-08-27 ｜ 状态：draft
> 定位：M5 上云前验证百万级并发设计目标；M2 起逐步搭建测试资产。
> 关联：docs/engineering/01-development-standards.md §4（测试金字塔/压测）

---

## 1. 目标与指标

**目标**：验证系统在目标负载下满足 SLO，定位瓶颈，给出扩容建议。

| 指标 | 目标（设计值，M5 以实测校准） |
| --- | --- |
| 可用性 | >= 99.95%（压测期无不可恢复故障） |
| 网关吞吐 | 弹性扩展支撑百万级并发接入；单实例验证其上限 |
| 非流式请求 P95 | < 500ms（网关→模型链路，不含模型生成） |
| 流式首 token | P95 < 2s |
| 检索（RAG）P95 | < 300ms |
| 工具调用 P95 | < 1s |
| 错误率 | < 0.1%（非限流错误） |
| 长任务 | 10k 并发提交下任务不丢不重（幂等） |

## 2. 工具选型

| 工具 | 用途 | 说明 |
| --- | --- | --- |
| k6 | 网关/API 吞吐压测 | 脚本化、可入 CI、云端可扩展 |
| Locust | 复杂业务场景（流式/多步 agent） | Python，与团队技术栈一致 |
| ghz | gRPC（如内部服务启用） | 预留 |
| 观测配套 | Prometheus/Grafana + OTel | 压测即观测 |

## 3. 压测场景（P1-P6）

| 编号 | 场景 | 说明 | 重点指标 |
| --- | --- | --- | --- |
| P1 | 模型网关吞吐 | /v1/chat/completions 非流式/流式混合 | QPS、P95、错误率 |
| P2 | 任务流式 | Web 发起任务→SSE 事件流 | 首 token、吞吐、断连率 |
| P3 | RAG 检索 | /v1/kb/search 并发 | P95、命中率、召回 |
| P4 | 工具调用 | 多步 agent 频繁调工具 | 工具 P95、成功率 |
| P5 | 长任务并发 | 10k 任务并发 + 沙箱执行 | 队列深度、幂等、不丢不重 |
| P6 | 全链路混合 | 真实用户混合负载 | 端到端 SLO、扩容有效性 |

## 4. 容量模型（粗略估算）

```
单请求 token 吞吐模型：所需并发 = QPS × 平均生成耗时
网关层：无状态，HPA 按 CPU/在途请求扩容
模型层：RPS = 单卡并发 × 卡数；按 token/s 规划 GPU（vLLM 连续批处理）
瓶颈判定顺序：网关 → 模型 → 检索 → 沙箱 → 存储
```

- 以"百万级并发接入"为设计目标：接入层无状态水平扩展，会话/状态外置，队列削峰（架构总览 §4/§5）。
- 压测验证的是**弹性能力**（目标负载下扩容生效、SLO 达标），而非恒定百万同时在线。

## 5. 执行阶段

| 阶段 | 内容 | 环境 |
| --- | --- | --- |
| S1 冒烟 | 单用户功能 + 正确性 | 本地/dev |
| S2 基线 | 单实例指标基线（P1/P2） | dev/staging |
| S3 递增 | 阶梯加压找拐点 | staging |
| S4 长时间 | 稳定负载 30-60min 找内存泄漏/慢查询 | staging |
| S5 峰值/故障 | 突发流量 + 注入故障（Chaos）验证熔断/降级 | staging |
| S6 容量验收 | 目标负载 + 扩容验证，输出报告 | 上云前 |

> 每次压测必须：全程 OTel 观测 + 结果入报告 + bad case 回流。

## 6. 验收标准（DoD）

- [ ] 目标负载下全部 SLO 达标（§1 表格）
- [ ] HPA 扩容在 5 分钟内生效且无雪崩
- [ ] 压测报告：指标曲线、瓶颈定位、扩容建议、成本估算
- [ ] 无严重故障（无数据丢失、无越权、无不可恢复错误）
- [ ] 压测资产（脚本/数据/报告模板）入库可复跑

## 7. 与里程碑关系

- M2 起：搭建压测目录 `tests/load/`，P1/P2 脚本先行。
- M5 上云：执行 S1-S6，产出容量报告作为上线闸门之一。
