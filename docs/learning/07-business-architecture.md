# Flare Agent · 业务架构（实践 + 真理）

> 版本：v1.0 ｜ 日期：2026-08-27 ｜ 状态：draft
> 定位：回答"为谁、为什么存在、业务怎么运转"——目标、价值、能力、流程、对象、角色、商业模式。
>  业务架构是功能架构的上游（先想清楚做什么，再谈怎么实现）。配套：06-功能架构、08-技术架构。

---

## 1. 什么是业务架构（先立概念）

- 真理：业务架构 = 用业务语言回答五个问题：
  1. 为谁服务（客户/用户细分）；
  2. 提供什么价值（价值主张——别人为什么用我们）；
  3. 靠什么能力（业务能力地图）；
  4. 怎么运转（端到端业务流程 + 角色 + 规则）；
  5. 怎么长期活（运营/商业模式/合规/SLA）。
- 反面（避免）：直接跳到技术选型，不做业务分层——结果常是"能做但没人用、上线但不赚钱"。

## 2. 业务目标与价值主张

- 真理：价值主张要说清"对谁、解决什么痛点、好在哪里"，而不是堆功能。
- Flare Agent 的定位：面向企业与开发团队的**企业级 AI Agent 平台**——
  - 对谁：需要把 AI 放进生产流程的团队（开发/运维/客服/知识管理）；
  - 痛点：裸调 LLM 无记忆、无工具、无治理，做不成"能干活"的 Agent；
  - 价值：可运维、高可用、可拓展、带 RAG/记忆/工具/沙箱的一站式平台（对标 Codex/Claude Code/DeepSeek Harness）；
  - 好在哪里：分层记忆 + 上下文工程（回答更贴上下文）+ 知识库可溯源 + 工具/MCP 生态 + 阿里云底座。

## 3. 业务能力地图（Business Capability Map）

- 真理：能力地图按"能力是否稳定"分层——核心能力决定差异化，通用能力决定成本。
- Flare Agent 能力地图：

  核心差异化能力：
    ├─ Agent 编排（ReAct 决策、预算、检查点、人工介入）
    ├─ 分层记忆（短期对话 / 长期事实 / 向量记忆 + 上下文工程）
    ├─ RAG 知识库（入库管线 / 语义检索 / 引用溯源 / 评测）
    └─ 工具 / MCP / Skills 生态
  通用支撑能力：
    ├─ 身份与多租户（RBAC、project_id 隔离、配额）
    ├─ 模型网关（多供应商、降级、成本）
    ├─ 沙箱（安全执行代码/命令）
    └─ 观测 / 审计 / 计费 / 告警

- 决策含义：核心能力自己打磨（差异化），通用能力优先用云托管（PG/Redis/OSS/ARMS 买服务不造轮子）。

## 4. 端到端业务流程（一次完整业务的闭环）

    客户注册 → 创建组织/项目（租户隔离）
      │  运营：配额、成员、权限
      ▼
    搭建知识资产：上传文档 → 入库 → 检索验证（RAG 质量）
      │  知识运营：增删改、版本、质量评测（M3c）
      ▼
    日常使用：提问 → Agent 完成任务（查知识/记记忆/调工具）
      │  会话运营：续聊、纠错、反馈
      ▼
    沉淀与治理：记忆沉淀、审计日志、SLA 达成、成本看板
      │  平台运营：告警、容量、回滚（M6）
      ▼
    持续改进：评测回归 → 知识/提示词/模型迭代

- 每条业务活动都要能回答"落在哪个功能域"——业务流程图是功能架构的来源。

## 5. 业务对象（核心数据模型，业务语言版）

- 真理：业务对象是先于数据库的"业务名词"，技术表是实现它的载体。对象清单要稳定，表可以演进。
- Flare Agent 业务对象：
  - 用户 / 成员：谁能用（身份）；
  - 组织 / 项目：隔离边界（多租户），事实/文档/会话都挂在 project 下；
  - 会话（thread）：一次持续对话的边界（短期记忆的作用域）；
  - 任务（task）：一次 Agent 执行的单元（有输入/轨迹/结果/状态）；
  - 文档 / 片段（doc/chunk）：知识库的源与最小检索单元（带来源可溯源）；
  - 事实（fact）：项目级长期记忆（key->value，精确读写）；
  - 笔记（note）：向量记忆（语义召回，可读溯源）；
  - 工具（tool）：Agent 可调用的能力（schema + 实现）。
- 关系：组织→项目→{会话→任务→（文档/事实/笔记）}；用户→组织（多对多，RBAC）。

## 6. 角色与权限（RBAC）

- 真理：角色是权限的打包，权限落到"对象 x 动作"（如：项目管理员可删文档，成员只能读）。
- 角色模型（建议，M5 落地）：
  - 平台管理员：租户管理、配额、审计、全局配置；
  - 项目管理员：项目内成员/知识/记忆/工具管理；
  - 项目成员：发起任务、读写项目内知识/记忆；
  - 访客（只读）：查看结果、检索知识。
- 现状：数据层已按 project_id 隔离（facts/向量/知识库）✅；身份与 RBAC 头（X-Tenant-Id）M5 ⏳。

## 7. 多租户业务模型

- 真理：多租户 = 数据隔离 + 配额（资源不打架）+ 计量计费 + 审计（出事能追）。
  隔离策略分三档：独立部署（最贵最安全）/ 独立数据库 / 共享库按 tenant_id 过滤（经济、默认）。
- Flare Agent：起步共享库 + project_id 隔离（已实现），M5 加 tenant_id 维度 + 配额/计量；
  极端合规场景（金融）再考虑独立实例。

## 8. 运营与商业考量

- 配额与计费：按"模型调用量 / 任务数 / 存储量 / 席位"计费（LLM 成本是最大变量，要透传到计费）；
- SLA 承诺：可用性 99.9%、P95 首 token < 1s（见 learning/05 §8 SLO）；
- 合规与审计：操作日志留痕、知识库内容审核、数据可删除（GDPR 类要求）；
- 成本治理：任务预算（max_steps）+ 上下文预算（F4.3）是成本护栏。

## 9. 业务 → 功能 → 技术 一条线贯穿

- 示例：业务需求"销售团队要基于产品文档回答问题"：
  - 业务层：角色=项目成员；流程=上传文档→提问→带引用回答；
  - 功能层：知识库域（入库/检索/溯源）+ 会话任务域（提问链路）+ 记忆域（沉淀）；
  - 技术层：rag 管线 + SqliteVectorStore/PgVectorStore + kb_search 工具注入 system 提示（R1）。
- 三层任一层的变更都要回看上下游——业务改流程，功能加能力，技术换实现。

3. 判断：把"沙箱"归为通用支撑能力还是核心能力？给出你的理由。
