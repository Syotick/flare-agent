## 1. 什么是功能架构（先立概念）

- 真理：功能架构 = 从"用户能做什么"出发的功能分解，**按内聚分域、按依赖排序**。
  它不是功能的堆砌清单，而是回答：有哪些功能域（Domain）、域内有哪些功能（Capability）、
  功能之间怎么协作（Flow）。好的功能架构 = 一个用户目标只需走一条清晰的链路。
- 反面（避免）：功能平铺在一个大池子里、互相直接调用、没有边界——加一个功能动全身（耦合），
  换个渠道（Web/CLI/API）全要重做（没有统一能力层）。

        │                                                     │        │

        │                                        （记忆/知识/对话三层）  （kb_search/mem_set/mem_recall + 注册表）
        │                                                     │        │
        ▼                                                     ▼        ▼
    知识库域（文档入库/检索/溯源）  ＋  记忆域（事实/向量/短期）     模型网关域（多供应商、mock→真实）
        │                                                     │
        ▼                                                     ▼
    管理运维域（配置/健康/审计/日志/监控） ◄── 观测与治理（横切）──► 沙箱域（代码执行，M4）

- 8 个功能域：用户组织 / 会话任务 / Agent 执行 / 知识库 / 记忆 / 工具 / 模型网关 / 管理运维（+沙箱）。
- 原则：**能力域之间只通过服务接口协作**（如工具域调用知识库检索、记忆域调用向量存储），
  域内细节不外泄——这是"加功能不伤别处"的结构保证。

## 4. 核心功能闭环（一次提问全链路）

    用户提问（Web/CLI/API）
      │  1. 发起任务：立即返回 task_id（不阻塞）
      ▼
    上下文工程域：按 task_input 召回 记忆(事实+向量) + 该线程近期对话，拼成上下文块
      │  2. 注入首个 user 消息（graph.memory_context）
      ▼
    Agent 执行域：模型决策 → 需要工具？
      │  3a. 是 → 工具域执行（kb_search 查知识库 / mem_recall 回忆 / mem_set 记住）→ 观察回灌 → 回到决策
      │  3b. 否 → 生成最终答案
      ▼
    结果回流：状态 + SSE 事件 + 检查点落盘（thread 可续聊）
      │  4. 任务详情 / 实时轨迹可查
      ▼
    记忆沉淀：模型可 mem_set 把约定写进长期事实（显式通道）

- 这条链路里，**上下文工程域是"总装车间"**：它决定模型能看到什么（记忆/知识/对话），
  直接决定回答质量——所以它要遵守"预算 + 相关性 + 优先级"三条纪律（见 learning/03）。

## 5. 功能间依赖（谁调用谁）

- 会话任务域 → Agent 执行域（起任务）→ 上下文工程域 / 工具域 / 模型网关域；
- 工具域 → 知识库域（检索）、记忆域（读写）、沙箱域（执行代码，M4）；
- 知识库域 / 记忆域 → 存储（向量/事实/文档，开发 SQLite、生产云底座）；
- 所有域 → 观测与治理（日志/指标/审计）。
- 依赖方向一旦确定，**新增功能 = 加在某个域内 + 只依赖下层**，不许跨域直连（见 learning/04 §1）。

## 6. 非功能需求落到功能上（NFR 不是口号）

- 可运维：每个功能域都有健康检查与日志，/health 探活（NFR）；
- 高可用：任务不落单机（M5 迁 Redis/PG），会话可恢复续聊（checkpoint）；
- 可拓展：能力域走接口，换存储/换模型只动实现类（learning/04 §5 协议可插拔）；
- 安全：CORS 白名单、密钥进 Secret、多租户 project_id 隔离（learning/05 §6）；
- 成本：模型调用受 max_steps 预算 + 上下文预算约束（F4.3）。

## 7. 三层架构的关系（功能 ↔ 业务 ↔ 技术）

- 业务架构说"为谁、为什么、怎么运转"（目标、角色、流程）；
- 功能架构说"提供什么能力、能力怎么组织"（功能域、功能、链路）；
- 技术架构说"用什么实现、怎么部署"（技术栈、组件、拓扑）。
- 一条需求贯穿三层示例：FR-5 知识库 → 功能层"文档入库/检索溯源" → 技术层
  "rag 管线 + SqliteVectorStore/PgVectorStore + HashEmbedder/DashScopeEmbedder"。
  三层对齐，需求才不会"实现走样"。
