# ADR-0015 · 工程结构：Monorepo + 模块化单体优先

> 状态：accepted
> 日期：2026-08-27
> 决策人：Syotick（用户确认）
> 关联：docs/product/architecture/02-module-design.md

## 背景（Context）

单人全栈起步、目标是企业级/百万级并发；需要在"开发效率"与"未来拆分能力"之间取舍。

## 备选方案（Options）

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 模块化单体 + Monorepo | 开发快、共享 common、边界清晰、按需拆分 | 初期单体部署，拆分需重构成本 |
| 一步到位微服务 | 独立扩缩 | 单人维护成本高、调试难、发布复杂 |
| 单一大单体 | 最简单 | 边界模糊，难以演进 |

## 决策（Decision）

- 选择：**Monorepo + 模块化单体优先**（services/ 内为可独立启动的 app + 共享 common，先单进程部署）
- 理由：开发效率优先，模块边界与 API 已按可拆分设计；M4/M5 按服务拆分部署。

## 后果（Consequences）

- 正面：快速迭代、共享 SDK/观测、边界清晰。
- 代价：拆分时按边界切割（服务已独立 app，成本可控）。
- 迁移/回滚：docker-compose 可一键把各 app 分别启动，天然支持拆分。
